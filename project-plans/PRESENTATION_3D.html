The problem

Two repos. One product. A weekend lost to merge hell.

You found a killer library on GitHub. You want its feature in your app. You start by copy-pasting files. Within an hour, you're neck-deep in broken imports, conflicting dependencies, and license files you can't legally ignore. The "just merge them" answer is naive.

Every team that combines two open-source projects writes the same brittle glue. They write it differently, badly, and over and over. There is no good tool for this. Until now.

⚠️

Lost provenance

Files get rewritten. Original authors and licenses go uncredited. MIT and Apache require attribution; GPL and AGPL carry obligations most teams don't even know they have.

💥

Dependency chaos

Two package.jsons. Three lockfile formats. Semver ranges that don't agree. The version of lodash in repo A is two majors behind the one in repo B, and neither can be downgraded safely.

🐹

Manual grind

Filter-repo, subtree, cherry-pick, refactor, retest, document. The whole loop takes two days of careful, error-prone work. One typo and you have a regression no one notices for three months.

The hardest part of open source isn't writing the code. It's combining two projects without breaking either one.
The solution

One command. Repo A + Repo B → Repo C with a PR.

You point repo-stitcher at two repos. It uses git-filter-repo to extract the paths you want from each, fuses them into a third repo, resolves the dependency union, runs a license compatibility check, builds the result in a sandbox, and opens a PR on GitHub with a generated CREDITS.md and SBOM.

Every step is observable. Every step is gated. The AI agent proposes edits and your terminal shows them; nothing lands in main without your say-so.

🧬

Git-native extraction

git-filter-repo with provenance tags. Every file keeps its origin commit, its original author, and its original license. The history isn't lost — it's preserved as a notes/refs graph in the new repo.

🤖

AI agent loop

LLM with 10 tools: select_files, resolve_dependency_closure, detect_ecosystem, apply_fix, edit_file, propose_component, run_build, and more. Self-critique confidence scoring decides what to auto-apply vs. what to gate for human review.

🛡️

Safe by default

Sandboxed Docker builds. SPDX license scan with a configurable compatibility policy. Per-ecosystem test runners. The result has to pass the test suite before it touches your PR.

Tech stack

Modern, type-safe, monorepo.

No guessing. Every dependency is fixed in package.json. Bun + TypeScript strict + React 18 + Ink. The whole thing ships as a single binary compiled by bun build --compile. You can run it without Node installed.

Architecture

Three packages. One frozen contract.

The CLI and Web are thin user interfaces over a single core package that holds all the business logic. After Wave 0, the core public API is frozen — no breaking changes without a version bump. This contract is what lets two developers work in parallel without stepping on each other.

Owner model

Two developers, two ownership lanes, zero merge conflict on the contract.

  • inbesat owns core, root config, and all project-plans/ documentation
  • aradhy owns cli and web, consuming the frozen API
  • Both can add features to core via PR, but only inbesat merges breaking changes
  • Dependency requests flow aradhy → inbesat through a tracked issue
  • The packages/shared types are the only file the two owners both read but neither edits unilaterally

What lives where

The package boundary mirrors the dependency direction. Nothing in core imports from cli or web. The CLI and Web packages never talk to each other except through the contract.

  • core knows about git, GitHub, dependencies, licenses, AI providers, sandboxes, and provenance
  • cli knows about terminal interaction, command parsing, and the local HTTP/WS server
  • web knows about React, routing, real-time WebSocket streams, and accessibility
  • Configuration is loaded in core via a Zod-validated ConfigSchema; both UIs pass user input to it
The roadmap

Four waves. Nine weeks to MVP.

The work is split into four waves plus a research gap. Each wave has a clear owner lane, a clear exit criterion, and a clear handoff to the next.

WAVE 0

Foundation & all dependencies

Weeks 1–2 · inbesat only

Zero-conflict scaffold. Every dependency in the entire plan is installed and verified. The monorepo compiles. stitch doctor passes on a clean machine. The contract is frozen. A handoff package is written.

What gets built: the Bun monorepo, TypeScript strict config, ESLint + Prettier, Vitest setup, Husky pre-commit hooks, Changesets for versioning, a CI skeleton, a Dockerfile, the Pino logger, the neverthrow Result type, the Zod-validated ConfigSchema, and 68 phases of individual dependency installation — every npm package and every system tool documented and verified by stitch doctor.

What gets written: ARCHITECTURE.md, CONTRIBUTING.md, a git branching model doc, a contract-freeze gate script, a packages/shared module for cross-cutting types, a HANDOFF.md for aradhy, and a dep-request flow that lets aradhy file issues for missing packages without touching package.json.

Exit criterion: aradhy can clone the repo, run bun install, run stitch doctor, and start Wave 1 without modifying any root file.

WAVE 1

Parallel core + CLI/Web

Weeks 3–6 · both tracks in parallel

inbesat builds all the core logic. aradhy builds the CLI and Web UI against the frozen API. They never block each other. The WebSocket protocol between the Web UI and the CLI is the only place their code is aware of each other, and that's already frozen.

inbesat track (Epics 2–9, P-069–P-188): Git core operations (clone, filter-repo, merge, push), GitHub integration (auth, create repo, open PR), dependency union and semver resolution, SPDX license scanning with a compatibility matrix, the OpenRouter primary AI provider with Anthropic and Ollama fallbacks, a ten-tool agent loop with a state machine, a Docker-based sandbox runner with GitHub Actions fallback, and a complete provenance system that emits CREDITS.md, an SBOM, and git notes for every file in the target repo.

aradhy track (Epics 10–11, P-189–P-237): A Commander-based CLI with eight top-level commands (init, add, merge, serve, status, doctor, license, deps), an Ink-based TUI with theme support, an Elysia-based local HTTP and WebSocket server, and a React 18 web app with five pages (Source picker, File tree, Live review, Results, Settings), a file tree component, a diff viewer with syntax highlighting, and a real-time WebSocket stream that surfaces AI proposals for human-in-the-loop gating.

Exit criterion: stitch merge works end-to-end via the CLI on at least one real repo pair, and the same merge can be driven from the Web UI with the live stream rendering the same events.

WAVE 1.5

Research gap closure

Weeks 6–7 · mixed owners · gates & conditions

Before the MVP tag lands, we run a structured research program to validate the AI-stitcher against real-world repo pairs, conditionally extend its resolution capabilities, add confidence scoring so the human can trust the AI's auto-applied edits, and ship a first-class MCP server so AI hosts like Claude Code and OpenCode can drive stitcher directly.

Epic 16 — Eval Harness (P-320–P-333)

A corpus of 20 real-world repo pairs (5 per ecosystem: JavaScript/TypeScript, Python, Go, Rust) with pinned fixture SHAs for reproducibility. A stitch eval run command that runs the full pipeline on the corpus, scores build-pass via the existing sandbox, and scores a 1–5 human rubric via a rater review tool. The baseline run (P-327) is the go/no-go gate for the MVP: build-pass rate, average rubric score, and resolve rate are documented in EVAL.md. After baseline, a CI regression gate runs a subset on every PR and the full corpus on every release tag. A failure taxonomy (import-resolution, semver, license, loop-cap, sandbox-timeout, semantic-wrong) drives the conditional Epic 17.

Epic 17 — Cross-Language Resolution (P-334–P-345)

A generic LSP client (JSON-RPC over stdio) wrapping tsserver, pyright, gopls, and rust-analyzer. Per-language resolver modules. A heuristic tree-sitter fallback for when the LSP is slow or unavailable. A unified DependencyResolver interface that tags every resolution with confidence (LSP-high, heuristic-medium, unresolved). The whole epic is conditional on P-331: if the failure taxonomy shows import-resolution is a top-2 failure category, the LSP work is funded. Otherwise, the heuristic fallback alone ships.

Epic 18 — Confidence Scoring (P-346–P-356)

A SemanticConfidence schema (composite 0–100 with component breakdown, rationale, and flag list). A self-critique prompt design where the agent re-reads its own diff before scoring. A composite model: sandbox 30%, self-critique 25%, resolver confidence 20%, license scan 15%, test pass 10%. A threshold policy (default auto-approve at 75, force human-in-the-loop below). Confidence is visible in the CLI output, the Web UI badges, and the CREDITS.md per-file section. The P-354 calibration check measures correlation between self-confidence and human rubric; if rho < 0.5, P-355 runs a recalibration loop. CONFIDENCE.md documents that this is a heuristic, not a guarantee.

Epic 19 — MCP-First Distribution (P-357–P-366)

An MCP server in packages/mcp/ that exposes three tools (stitch_select_files, stitch_merge, stitch_check_license) over the Elysia HTTP transport. Progress streaming via notifications/progress. Auth and config pass-through that reuses ~/.stitch/config.json. A compatibility pass against Claude Code, OpenCode, and Cursor. Submission to the MCP registry so the server is discoverable by name. MCP_QUICKSTART.md shows how to go from a blank Claude Code conversation to a merged PR in one turn. Opt-in telemetry compares MCP vs CLI vs Web usage. This epic supersedes P-299 (the older "MCP server for OpenCode" wave-3 phase), which is now marked superseded in PROGRESS.md.

WAVE 2

Integration, quality, docs

Weeks 8–9 · coordinated, file-isolated

This is the MVP release wave. The pipeline orchestration, the test matrix, the CI, the docs, and the packaging all land here. The v1.0.0 tag is cut at the end of this wave.

Orchestration (Epic 12, P-238–P-252): A pipeline state machine that drives a job through every stage. A bun:sqlite job queue with retry and rollback. A WebSocket event bus that the Web UI subscribes to. A contract test that fails CI if the frozen core API drifts.

Testing + CI (Epic 13, P-253–P-267): Unit tests, integration tests against fixture repos, and Playwright e2e tests for the Web UI. A CI matrix on Linux, macOS, and Windows. Per-package coverage thresholds (80% core, 70% CLI, 80% web, 80% shared). A bun audit pass and a manual security review of the sandbox and license policy gate.

Docs + packaging (Epic 14, P-268–P-282): A README.md with quickstart and screenshots. A QUICKSTART.md with copy-paste-runnable examples. An API reference generated by TypeDoc. A CLI reference generated from the Commander metadata. A web docs site. Publish to npm (both the stitch CLI package and the @repo-stitcher/core library), publish a Docker image, and cut GitHub Releases for all three platforms.

Exit criterion: stitch merge works end-to-end on 5 diverse repo pairs. The eval corpus composite score is at the agreed target. CI is green. Binary releases are downloadable. All docs are published.

WAVE 3

Advanced & extensibility

Post-MVP · split by component · demand-driven

After the MVP ships, the plan pivots to demand-driven prioritization. The phases in Epic 15 are pre-planned but not pre-scheduled. The team picks what to build based on what users actually ask for, what the analytics show, and what the marketplace signals.

19 sub-epics cover the platform features: a plugin system, ecosystem plugins for Go/Rust/Python, an AI connector plugin, a template library, smart presets, batch stitch, scheduled merges, multi-user server mode, RBAC, analytics dashboard, outgoing webhooks, REST and GraphQL APIs, a VS Code extension, offline model support, cost budgets, a repo-metadata cache, K8s sandbox, opt-in telemetry, SSO, compliance export, a plugin marketplace, benchmark suite, config migration, and i18n.

Plus the four research-gap epics (16–19) as ongoing work: the eval corpus grows, the LSP coverage extends, the confidence model recalibrates against new rubric data, and the MCP server gains tools and host integrations.

How we know it works

Success metrics for the MVP.

Each metric is measured, not estimated. If a metric is missed at the MVP tag, it triggers an ADR and a course correction — the team doesn't ship a metric the team can't defend.

⏱️

Time-to-green-C

< 5 min from stitch merge invocation to a sandbox-passed target repo. This is the user's perceived speed. The breakdown: filter-repo ~30s, dep resolution ~10s, AI loop ~90s, sandbox build ~120s.

✅

Merge success rate

> 80% of eval-corpus merges land in a sandbox-green state on the first attempt. The remaining 20% are gated for human review and counted separately.

🛡️

License detection

0% false negatives. GPL, AGPL, and any custom policy-denied license must always be flagged. False positives are acceptable; false negatives are not.

📋

Provenance completeness

100%. Every file in the target repo must map back to exactly one source commit, with original author and license preserved. No orphan files.

⚡

CLI cold start

< 2s for stitch --version on a fresh binary. Bun-compiled binaries are fast, but lazy-loaded modules matter.

🌐

Web UI TTI

< 3s time-to-interactive on the Web UI's main wizard page, measured by Lighthouse on a local server.

🧪

Test coverage

80%/70%/80%/80% Vitest thresholds — core, CLI, web, shared. Below the threshold, the build fails.

📊

Eval resolve rate

≥ [target]% — the composite score from the eval harness. The exact target is set after P-327 baseline, and is the basis of the MVP go/no-go decision.

Risk register

What could go wrong, and what we do about it.

An honest list. Every risk has a mitigation, not a hope. Some risks are accepted on purpose — the plan names them so the team doesn't pretend they don't exist.

git-filter-repo on Windows
Likelihood: Med · Impact: High

Test on Windows early (P-087). Document Python install + pip install git-filter-repo workarounds. Have a fallback to git subtree for the most common cases.

OpenRouter Gemini 3 bug
Likelihood: Known · Impact: Med

Documented in the model registry. Default to Claude via OpenRouter; test the other models against the eval corpus before promoting them to defaults.

Docker not on CI
Likelihood: Low · Impact: Med

GitHub Actions fallback is implemented in P-175. The sandbox always has a non-Docker path on CI runners.

AI token cost overrun
Likelihood: Med · Impact: Med

Per-job 500k token budget. Alert at 80%. Cost-per-merge tracked per run in the eval harness (P-330). Auto-swap to a cheaper model when budget is tight.

Eval corpus reveals low resolve rate
Likelihood: Med · Impact: Critical

P-327 baseline is the go/no-go gate for the MVP. If the composite score is below the target, the MVP tag is delayed. Epic 17 (LSP resolution) is the conditional response. Worst case: shift to "human review required" as the default mode.

LSP startup cost
Likelihood: Med · Impact: Med

Heuristic tree-sitter fallback (P-340) is the primary path. LSP warm-server caching (P-344) is the optimization. Worst case: ship heuristic-only and document the LSP path as experimental.

Self-confidence uncorrelated with human rubric
Likelihood: Med · Impact: High

P-354 calibration is the gate. P-355 recalibration loop iterates on prompt and weights until rho ≥ 0.5. CONFIDENCE.md documents the heuristic honestly — confidence is a hint, not a guarantee.

Merge conflicts between dev owners
Likelihood: Low · Impact: High

Package isolation by directory ownership. The contract is frozen in packages/shared via the P-314 contract-freeze gate. CI fails on contract drift.

The pitch

Stop merging. Start stitching.

Open-source has a composition problem. Every team that wants to combine two libraries writes the same brittle glue. repo-stitcher turns that into a one-line command — with provenance, license safety, and a working sandbox build, not just a zip of files.

You point it at two repos. It uses git-filter-repo to extract the paths you want. It resolves the dependency union, runs a license compatibility check, and produces a target repo with full CREDITS.md, an SBOM, and a passed sandbox build. It opens a PR. You approve. Done.
